기능 구현, 버그 수정, 기능 수정, 개선사항 등 모든 작업에 동일하게 적용:
1. 원인/요구사항 분석
2. 기존 시스템과 코드를 충분히 활용한 합리적 방안 모색 (중복 코딩, 불필요한 복잡성 금지)
3. **방안 제시 시 다음 4가지를 디자이너가 알아듣기 쉬운 친숙한 언어로 명시**:
   - 어느 **씬(Scene) 또는 프리팹(Prefab)**에 작업할지
   - 그 안의 **어느 GameObject/오브젝트**에 적용할지
   - **어떻게 반영**할지 (어떤 컴포넌트의 어떤 필드, 어떤 동작 변경 등)
   - 디자이너 입장에서 그 변경이 시각/조작 측면에서 어떤 결과를 낳을지
4. 사용자 이해 확인 후 **명시적 허가**를 받고 수정 진행

**자동화 원칙 — 금지선과 허용선 명확히 구분**

금지선(Claude가 절대 사용자에게 요구하면 안 되는 것):
- **cs 파일/스크립트의 프로그래밍 언어 코드를 사용자에게 직접 작성하라고 요구하는 것** — 이게 핵심 금지선.
- 새 cs 파일 생성, 코드 로직 작성, 컴파일러 수준 작업은 모두 Claude가 자동 처리.

허용선(사용자에게 부탁하거나 안내해도 되는 것):
- **Unity 에디터에서의 간단한 GUI 작업** — 디자이너 본업 영역이라 사용자가 직접 처리 가능:
  - Hierarchy에서 GameObject 만들기/이름 바꾸기
  - Inspector에서 컴포넌트 부착 / 필드에 오브젝트 드래그&드롭 / 슬라이더·체크박스 조정
  - 프리팹 자식 구조 변경, sibling order 조정
  - Button OnClick 연결 같은 단순 와이어링
  - Play 버튼 누르기, 시각 확인
- Claude가 **prefab/scene YAML을 직접 편집해도 되지만, 그게 디자이너의 평범한 GUI 작업이면 사용자에게 맡겨도 무방**.

**Why:** 사용자는 Unity 디자이너로 GUI 조작은 능숙하다. 모든 작업을 Claude가 혼자 처리하려 들면 (1) 사용자 직무 영역을 침범해 자기 결정권을 빼앗고 (2) 단순 작업도 prefab YAML 편집 같은 위험한 방식으로 처리해 부작용 위험이 커진다. 진짜 금지는 "디자이너에게 cs 코드를 작성하라고 요구"하는 것 — 이건 Claude Code의 상품 가치를 본질적으로 훼손.
**How to apply:** 작업을 받으면 먼저 (1) **cs 코드 작업이 필요한가?** → Claude가 자동 처리. (2) **Unity GUI 작업(컴포넌트 부착·필드 연결·자식 생성 등)인가?** → 사용자에게 "어느 씬/prefab의 어디에 무엇을 어떻게 하면 됩니다"를 친숙한 한국어로 안내. 사용자가 "내가 할게"하면 안내만, "네가 해줘"하면 Claude가 prefab YAML 직접 편집. **사용자의 디자이너 본업 영역(간단 GUI)을 Claude가 자동 침범하지 말 것.**
